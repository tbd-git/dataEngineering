Here are practical examples for each of the PySpark / Apache Spark optimization techniques you mentioned.

## 1. Use Appropriate Partitioning

Partitioning determines how your data is divided across cluster nodes. Partitioning by high-cardinality columns (or creating too many tiny partitions) leads to overhead, while under-partitioning underutilizes the cluster.

### ❌ Unoptimized (Too many or poor partitions)

```python
# Creates 200 default partitions for a tiny dataset, wasting memory overhead
df = spark.read.csv("s3://my-bucket/small_data.csv")
print(df.rdd.getNumPartitions())  # Default usually 200

```

### ✅ Optimized Example

Use `coalesce()` to reduce partitions (avoids full shuffle) or `repartition()` to evenly redistribute data by a specific join/filter key.

```python
# Reduce partitions without a full shuffle for smaller data
df_coalesced = df.coalesce(4)

# Repartition data on a frequently queried column before heavy operations
df_repartitioned = df.repartition(10, "department_id")

# Save to S3/HDFS partitioned by date for faster downstream partition pruning
df_repartitioned.write.partitionBy("date").parquet("s3://my-bucket/processed_data/")

```

## 2. Broadcast Small Tables in Joins

By default, joining two DataFrames causes a **SortMerge Join**, which shuffles large amounts of data across the network. If one table is small (typically < 10MB to a few hundred MBs), broadcasting it sends the small table to every executor, avoiding network shuffles entirely (**Broadcast Hash Join**).

### ❌ Unoptimized (Standard Shuffle Join)

```python
# Causes a expensive network shuffle for both large_df and small_df
joined_df = large_df.join(small_df, on="dept_id", how="inner")

```

### ✅ Optimized Example

```python
from pyspark.sql.functions import broadcast

# Broadcasts small_df to all nodes; large_df stays in place without shuffling
joined_df = large_df.join(broadcast(small_df), on="dept_id", how="inner")

```

## 3. Cache Reused DataFrames

If you compute a complex DataFrame and use it multiple times downstream, Spark will recompute the entire execution lineage every single time by default. Caching keeps the computed DataFrame in executor memory/disk.

### ❌ Unoptimized (Recomputes lineage twice)

```python
filtered_df = large_df.filter(large_df["status"] == "ACTIVE").select("user_id", "salary")

# Lineage for filtered_df runs HERE
count_active = filtered_df.count()

# Lineage for filtered_df runs AGAIN from scratch HERE
filtered_df.write.parquet("s3://my-bucket/active_users/")

```

### ✅ Optimized Example

```python
from pyspark.storage import StorageLevel

filtered_df = large_df.filter(large_df["status"] == "ACTIVE").select("user_id", "salary")

# Cache in memory (or use .persist(StorageLevel.MEMORY_AND_DISK) for large datasets)
filtered_df.cache()

# First action triggers computation and fills cache
count_active = filtered_df.count() 

# Second action reuses memory cache instantly
filtered_df.write.parquet("s3://my-bucket/active_users/")

# Always unpersist when finished to free up cluster memory!
filtered_df.unpersist()

```

## 4. Avoid Unnecessary Wide Transformations

* **Narrow Transformations:** Operations like `filter()`, `map()`, and `select()` happen within a single partition without moving data across nodes.
* **Wide Transformations:** Operations like `groupBy()`, `distinct()`, `join()`, and `reduceByKey()` require moving data between nodes across the network (**Shuffle**), which is slow.

### ❌ Unoptimized (Unnecessary Wide Transformation)

```python
# Distinct causes a full shuffle across the network just to count unique users
unique_count = df.select("user_id").distinct().count()

# GroupBy before filtering forces all rows to be shuffled across nodes first
grouped = df.groupBy("country").agg({"salary": "avg"}).filter("country = 'US'")

```

### ✅ Optimized Example

```python
# Alternative: Filter FIRST (Narrow) to drop unwanted rows BEFORE performing wide transformations
filtered_df = df.filter(df["country"] == "US")

# Now the groupBy shuffle only moves US-based records across nodes
grouped = filtered_df.groupBy("country").agg({"salary": "avg"})

# Using approx_count_distinct avoids a full expensive shuffle for giant datasets
from pyspark.sql.functions import approx_count_distinct
approx_unique_count = df.select(approx_count_distinct("user_id")).collect()

```

## 5. Tune Executor Memory & Cores

Submitting a Spark job without tuning resources can lead to **Out-Of-Memory (OOM)** errors (executors too big/overloaded) or **Garbage Collection (GC) pauses** (executors too large).

Rule of thumb for Spark tuning: Keep executor cores between **3 to 5** for optimal I/O throughput and memory management.

### ❌ Unoptimized (`spark-submit` defaults)

```bash
# Running with 1 core per executor results in poor parallel execution, 
# while setting 16 cores per executor causes severe GC overhead.
spark-submit \
  --master yarn \
  --num-executors 2 \
  --executor-cores 1 \
  --executor-memory 1g \
  my_script.py

```

### ✅ Optimized `spark-submit` Configuration Example

```bash
spark-submit \
  --master yarn \
  --num-executors 10 \
  --executor-cores 4 \
  --executor-memory 8g \
  --driver-memory 4g \
  --conf spark.memory.fraction=0.8 \
  --conf spark.sql.shuffle.partitions=200 \
  my_script.py

```

* **`--executor-cores 4`**: 4–5 cores per executor balances multi-threading and GC performance.
* **`--executor-memory 8g`**: Allocates enough RAM per container to hold partitions in memory.
* **`spark.sql.shuffle.partitions=200`**: Controls the number of partitions created during wide transformations/shuffles (adjust based on total data size).
